# Deployment Guide

This app deploys as three pieces: a **PostgreSQL** database, the **Express API**,
and the **React static frontend**. The repo ships a [`render.yaml`](../render.yaml)
blueprint that provisions all three on [Render](https://render.com) from a single
GitHub connection — no CLI or local Docker required.

> Any host works (Railway, Fly.io, Neon + Vercel, a VPS, …). The blueprint targets
> Render because it can host all three tiers together on a free tier. The
> environment variables below are the same wherever you deploy.

## Prerequisites

- The repo pushed to GitHub (done: `adwithanimma/mini-erp-crm`).
- A Render account (sign up with your GitHub login).

## One-time deploy (Render Blueprint)

1. In Render: **New → Blueprint**, then connect the `mini-erp-crm` repo.
   Render reads `render.yaml` and shows three resources: `mini-erp-db`,
   `mini-erp-api`, and `mini-erp-web`. Click **Apply**.
2. Wait for **`mini-erp-api`** to go live, then copy its URL
   (e.g. `https://mini-erp-api.onrender.com`).
3. Open **`mini-erp-web`** → Environment → set:
   `VITE_API_URL = https://mini-erp-api.onrender.com/api`  ← note the `/api`.
   Save; this triggers a rebuild of the frontend.
4. *(Optional, recommended)* Open **`mini-erp-api`** → Environment → set
   `CORS_ORIGIN` to the frontend URL (e.g. `https://mini-erp-web.onrender.com`)
   to restrict cross-origin access. If left unset, the API allows all origins.

## Load the database schema

The provisioned Postgres starts empty. Load the schema and demo data once, using
the database's **External Connection String** (Render dashboard → `mini-erp-db` →
Connect → External):

```bash
psql "<EXTERNAL_DATABASE_URL>" -f database/schema.sql
psql "<EXTERNAL_DATABASE_URL>" -f database/seed.sql
```

Then log in with a demo account (password `admin123` for all): `admin@test.com`,
`sales@test.com`, `warehouse@test.com`, `accounts@test.com`.

> **Change the demo password after first login**, and rotate `JWT_SECRET` if you
> ever exposed it. `JWT_SECRET` is auto-generated by the blueprint.

## Environment variables

| Service | Variable | Value | Set by |
| ------- | -------- | ----- | ------ |
| API     | `DATABASE_URL` | Postgres connection string | blueprint (auto) |
| API     | `JWT_SECRET`   | random secret              | blueprint (auto) |
| API     | `CORS_ORIGIN`  | frontend URL (optional)    | you |
| API     | `PORT`         | injected by host           | host (auto) |
| Frontend| `VITE_API_URL` | `<API URL>/api`            | you |

Locally, the API instead reads discrete `DB_HOST`/`DB_PORT`/`DB_USER`/
`DB_PASSWORD`/`DB_NAME` from `backend/.env` (see `backend/.env.example`), and the
frontend falls back to `http://localhost:5000/api` when `VITE_API_URL` is unset.

## Manual / other-host notes

Build and run commands, if you deploy somewhere without the blueprint:

| Piece    | Build                          | Run / publish                 |
| -------- | ------------------------------ | ----------------------------- |
| API      | `npm install && npm run build` | `node dist/src/server.js`     |
| Frontend | `npm install && npm run build` | serve `frontend/dist` (static, with SPA fallback to `index.html`) |

## Free-tier caveats (Render)

- Free web services **spin down after ~15 min idle**; the first request afterward
  is slow (cold start) while the API wakes up.
- Free Postgres has storage/retention limits and may expire — fine for a demo, not
  for real data. Upgrade the database plan for production use.
